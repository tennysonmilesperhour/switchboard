### 2.1 CI has been dead since 08-29 and nothing blocked the merges

All three workflows (`CI`, `Database tests`, `Deploy database migrations`) have
failed on every push to `main` since 2026-08-29 16:31. The last green run was
2026-08-27 22:52. Every failed job completes in about three seconds with no log
content at all (the log download returns 404). That is the signature of GitHub
Actions declining to start a runner, which is almost always a billing or
spending-limit condition on the account, not a failing test.

Five commits merged in that window, including two with migrations:
`20260829120000_match_dismissals.sql` (#155) and
`20260829140000_calendar_subscriptions.sql` (#157). Vercel auto-deployed every
one of them to production (`switchboardsocial.me`, project `switchboard-hqk2`,
current deployment `f68181e`, READY). So the code that reads
`calendar_subscriptions` and `match_dismissals` is live and the pipeline that
would have created those tables never ran.

Nothing in the repo prevents this. The migration deploy runs in parallel with
the Vercel build, has no `concurrency` group, and no `environment:` protection
rule, so an app deploy never waits for its schema.

Update, later the same day: the CI run for this audit's own pull request
(#158, run 33570915910) started a runner and passed both jobs in seven
minutes. Actions works again as of September 1, which is when GitHub's
included minutes reset. That fits an exhausted monthly minutes allowance
better than any other explanation. The next push to `main` will re-run the
migration deploy, so check its log for what it applies and to which project
ref. The five commits from 08-29 through 08-31 were never CI-verified; the
local baseline in §2.4 covers `f68181e`, so they pass lint, types, unit tests,
and build, but the pgTAP suites for `match_dismissals` and
`calendar_subscriptions` have not run anywhere.

### 2.2 The production schema does not match the repo, and the parity check cannot see it

Vercel runtime errors for the last seven days contain one dominant group:

```
{"area":"settings.appearance-read","userCode":"SB-LOOK-UNREAD",
 "message":"column profiles.notify_plans does not exist","code":"42703"}
```

Sixteen occurrences across two users, first seen 2026-08-20, last seen
2026-08-31 19:52, on `GET /settings` and `POST /settings`. That column comes
from `20260717230000_notification_preferences.sql`, merged on 2026-07-31.

Yet the deploy job's own log from 08-27 (the last one that ran) says
"Remote database is up to date" and the parity dry-run passed. A database the
deploy job believes is fully migrated is missing a column from July. The two
explanations are that `SUPABASE_PROJECT_ID` in GitHub secrets points at a
different Supabase project than `NEXT_PUBLIC_SUPABASE_URL` on Vercel, or that
the migration history table was repaired by hand without the DDL running. The
Switchboard Supabase project is not in the organization connected to this
session, so this could not be settled here. It needs a person with dashboard
access to compare the two project refs. The GitHub integration's "Supabase
Preview" check links to project `cuzgighqdzypntmhxrqc`, so that is the ref to
compare against the host in Vercel's `NEXT_PUBLIC_SUPABASE_URL`.

Update, after the merge: the migration deploy triggered by merging this
audit (run 33572456042, 23:46 UTC) again reported "Remote database is up to
date" with nothing to apply, even though the pipeline never pushed the two
August 29 migrations. In the same window, `GET /settings` on the production
deployment returned 200 with no error at 18:08 UTC on September 1, on the
same deployment that logged the missing column at 19:52 UTC the day before.
So the column exists in production now, and it got there by hand, not through
the workflow. That settles the immediate outage and sharpens the finding:
the migration history the deploy job reads can say "applied" for a migration
whose DDL never ran, and nothing in the pipeline detects that. The parity
check compares filenames to a history table, not the schema to the repo.
Whoever patched production should say what they ran, and the health check in
§2.3 should assert real columns, not version strings.

What users experience: `src/app/settings/page.tsx:63-72` documents that a
failed profile read "renders every field blank and every preference at its
default". So Settings has looked wiped for real users since 08-20, and
`updateNotificationPrefs` (`src/lib/actions/profile.ts:519-530`) fails on save
with an uncoded "Could not save" string. That save path uses neither `failure()`
nor `reportOperationalError`, which is exactly the situation the error-code
rule in `AGENTS.md` exists to prevent.

## 3. Security

Reference: `docs/SECURITY.md`. The foundations it describes are real and
test-guarded: every table has RLS, no UPDATE policy in the final migration state
lacks `WITH CHECK`, ownership columns are frozen by triggers,
`platform_moderators` is deny-all, definer bodies live in a `private` schema
with default privileges revoked, every text sink is encoded through
`src/lib/security.ts`, `bearerMatches` is constant-time and fails closed, the
CSP is nonce-based with HSTS preload, no server secret is `NEXT_PUBLIC_`, and
the SSRF guard in `safe-fetch.ts` is thorough.

The gaps cluster in one question the docs' litmus tests do not quite reach:
"may this caller act on, or learn about, that other person?"

### High (verified line by line)

**H1. Parental approval can be self-approved or hijacked.**
`src/lib/actions/parental-approval.ts:22-104` never checks that the invite
belongs to the caller or to the named event; every read and write goes through
the admin client. `resolve_parental_approval`
(`20260811120000_parental_approval.sql:57-118`) does not cross-check
`event_id`. A youth can request approval to their own address and approve
themselves, and because the action refuses a second request per invite, they
pre-empt the real guardian. Any account can also email arbitrary addresses
through this path with no rate limit.

**H2. Live location coarsening is defeated by exact distance.**
`20260718120000_live_location.sql:99-102` rounds latitude and longitude to
three decimals but returns `distance_m` computed from the raw coordinates. The
caller's own position is whatever the client posts
(`src/lib/actions/live-location.ts:370-445`, 300 updates per hour). Three
spoofed positions and three exact distances trilaterate a sharer to the metre.
`live_location.test.sql` asserts only the rounding.

**H3. Shared Moments ships every anonymous candidate's user id.**
`src/app/moments/page.tsx:70-112` attaches `userId` to every candidate
regardless of consent stage, and `profiles_select using (true)` resolves that id
to name, handle, avatar, and bio. `find_shared_moments` (`init.sql:521`, never
redefined) applies no block filter, and `expressCuriosity` pings any moment's
owner. Checking in at a café reveals everyone else there before any mutual
curiosity, and a blocked user can still see and ping the person who blocked
them.

**H4. The invite pipeline ignores blocks and lets hosts forge attendance.**
`create_event_atomic` and `addPeopleToEvent` (`src/lib/actions/events.ts:393-567`)
apply no `are_blocked` check, no connection requirement, and no invitee cap;
only `inviteConnectionNow` (`events.ts:617`) checks blocks.
`deliverInvitations` and `cancelEvent` send host-authored text to any
`guest_contact`, so the product is an open email and SMS relay. The
`invites_insert` policy (`20260710123000_cohost_policy_parity.sql:16-17`) checks
only that the caller is host, so a host can insert `status = 'accepted'` for any
profile id and that person appears in "Who's in".

### Medium

- **M1** `digest_items(uuid)` is granted to `authenticated`
  (`20260818160000_daily_digest.sql:66`) and returns anyone's unread
  notification titles.
- **M2** Pair-wise oracles (`are_blocked`, `are_connected`, `is_event_host`,
  `is_room_member`, `is_zone_member`, `is_platform_moderator`, and others) are
  executable by any signed-in user, exposing the block graph, the social graph,
  and the moderator list.
- **M3** `resolve_profile_contact` is callable directly; the 10 per hour
  throttle lives only in the TypeScript wrapper. Verified email or phone maps to
  an account.
- **M4** Password reset and resend-confirmation resolve the user through the
  self-writable, unverified `profiles.contact_email`
  (`src/lib/actions/auth.ts:419-452`) with `maybeSingle`. An attacker who sets
  their own contact email to the victim's address makes the lookup return two
  rows, which becomes `null`, which becomes "ok" with no email sent. For an
  unconfirmed account that is a dead end, which `docs/AUTH.md` forbids.
- **M5** No rate limit on discovery (Sonnet), plan parsing, or per-message
  extraction; `SECURITY.md` §9 says AI calls are limited.
- **M6** The sign-in limiter is keyed on the identifier only, so anyone can lock
  any account out. There is no IP-scoped limiting anywhere.
- **M7** The "own storage" URL check (`src/lib/server/media.ts:40-43`) matches
  the path only, so avatars and covers can point at an attacker host and
  harvest viewer IPs.

### Low and informational

`checkRateLimit` fails open on error or missing credentials
(`rate-limit.ts:9-22`); the share-link RSVP limiter is keyed on the public
token so any holder can exhaust it; uploads do not sniff magic bytes; raw
PostgREST error messages reach clients and URLs (`boards.ts:656`);
`contact_verification_requests.attempts` is written but never enforced; the
push-subscribe route accepts any endpoint URL; there is no in-app suspend or
ban action.

Counts: 0 Critical, 4 High, 7 Medium, 6 Low, 6 Info. Five items need runtime
or dashboard confirmation (direct GoTrue sign-up bypassing the app's account
creation, DNS rebinding in `safe-fetch`, `banned_until` enforcement, storage
`nosniff`, realtime RLS enforcement).

**What is genuinely strong.** No `any`, no `@ts-ignore`, no TODO anywhere in
70k lines. Client components never query tables (the five browser Supabase
clients are realtime-only). `src/lib/engine/*` is pure and fully tested. The
meta-tests that read the source (`errors.test.ts`, `features.test.ts`,
`share-link.test.ts`, `profile-column-grants.test.ts`, `csp.test.ts`) are the
standout practice in the repo. `supabase/seed.sql` documents the two production
bugs that shaped it. Every recent migration has a matching pgTAP file.

**What holds it back.**

- **No generated `Database` type.** `src/lib/types.ts` is a hand-maintained
  mirror and it is stale: `calendar_subscriptions`, `calendar_busy`, and
  `match_dismissals` are absent, and `Profile` lacks `appearance_custom`,
  `digest_*`, `appearance_theme`, `legal_terms_version`, and `timezone`. There
  are 31 row casts to paper over it. `seed.sql` records that this drift class
  has already shipped two production bugs. The missing-column error in §2 is a
  third.
- **The error registry is adopted by about a third of action files.** 23 of 35
  never call `failure()` or `reportAndFail()`; 164 codeless `{ ok: false }`
  returns exist, and operational ones slip through (`boards.ts:110,293`,
  `calendar-sync.ts:198`, all of `identity.ts`). `errors.test.ts` only scans
  `reportOperationalError` areas, so it cannot catch this.
- **The share-link invariant is re-derived once.** `src/app/join/[id]/page.tsx:169`
  computes `status === 'inviting' || status === 'confirmed'`, which excludes
  `deciding` while `ANSWERABLE_EVENT_STATUSES` includes it. This is the exact
  pattern `AGENTS.md` forbids, in a file that imports the authority module on
  line 10.
- **Four files outgrew review.** `EventWizard.tsx` (2,046 lines, 39
  `useState`), `actions/events.ts` (1,605 lines, 14 admin-client sites),
  `events/[id]/page.tsx` (1,256 lines, 26 queries, 36 awaits, 4 in parallel),
  `PeopleClient.tsx` (1,104 lines, six sections).
- **Tests miss the mutations.** 2 of 35 action files and 0 of 13 route handlers
  have unit tests. `e2e/invite-links.spec.ts`, which guards the repo's most
  repeated regression class, is not run by the authenticated CI job
  (`ci.yml:136` runs `authed.spec.ts` only).
- **Auth preamble drift.** 26 raw `getUser()` preambles remain alongside
  `require-user.ts`, with twelve distinct "not signed in" return shapes.
- **Small hygiene.** `leaflet` is a devDependency imported at runtime. Four
  exported server actions are never called and remain reachable POST endpoints
  (`setEventInviteLink`, `toggleParentalApproval`, `removeFollowUpPoll`,
  `isOfferedSlot`). Six server-only modules (`supabase/admin.ts`,
  `ai/claude.ts`, `server/email.ts`, `sms.ts`, `notify.ts`, `secret.ts`) lack
  `import 'server-only'`. `tsconfig.tsbuildinfo` is untracked and not ignored.

## 6. Reliability, data, and operations

- **The digest never runs.** `vercel.json` schedules only `/api/cron/cascade`.
  `src/app/api/cron/digest/route.ts:8` and `DOCKET.md:101` both say hourly.
- **Every moderator's account is undeletable.** `user_reports.resolved_by`
  (`20260713170000:20`) and `venues.reviewed_by` (`20260717230100:42`) reference
  `profiles(id)` with no `ON DELETE` clause. `auth.admin.deleteUser` fails on
  the FK and the user sees "Could not delete your account right now"
  (`auth.ts:685`). No pgTAP test exercises deletion.
- **No timeouts on outbound providers.** Resend (`email.ts:63`) and Twilio
  (`sms.ts:45`) `fetch` with no `AbortSignal`; the Anthropic client has no
  `timeout` (SDK default is ten minutes). `sendMessage`
  (`src/lib/actions/rooms.ts:46-62`) awaits the Haiku extraction before
  returning `ok`, so every room message pays model latency. Fan-out is
  unbounded `Promise.all`; Resend's 2 requests per second limit turns a 30-guest
  reminder into 429s that are logged and never retried. Nothing caps SMS spend.
- **Cron has no heartbeat and no overlap guard.** `checkRateLimit('cron:cascade', 5, 60)`
  permits five overlapping runs. Sweeps are sequential and bounded by
  `maxDuration = 60`, so at a few hundred live plans the function is killed
  mid-loop and no summary is produced.
- **Indexes.** There is no index on `events` at all (the cascade sweep filters
  `status = 'inviting'` every minute; plan lists filter by `host_id`). None on
  `push_subscriptions(user_id)` or `poll_votes(poll_id)`.
- **Sequential awaits.** `events/[id]/page.tsx` has around twenty independent
  reads run one after another; `settings/page.tsx` has seven. Vercel is pinned
  to `sfo1`; if the Supabase region differs, each pays a cross-continent round
  trip.
- **Retention.** Nothing sweeps `notifications`, `contact_verification_requests`
  (phone numbers past expiry), `rate_limits`, `usage_events`,
  `invite_delivery_attempts`, or closed `moments`. `live_locations` stores raw
  coordinates and coarsens only at read. Storage objects are orphaned on
  account deletion while `/privacy` promises removal.
- **Observability.** The webhook has no dedupe. Web-push failures other than
  404 and 410 are swallowed, so a rotated VAPID key kills push silently. Source
  maps are not uploaded, so client exceptions arrive minified.
- **Deploy workflow.** No `concurrency` group, no environment gate, no rollback
  procedure. `DEPLOYMENT.md:26-31` lists a `SUPABASE_DB_PASSWORD` secret the
  workflow does not use.

## 7. Privacy and compliance

The consent architecture is the strongest part of the product: mutual intents
only exist when mirrored, poll votes are author-only with aggregate functions,
live location is off by default, coarse, time-boxed, and audience-selectable,
zone presence crosses the boundary as an integer, moments reveal in three
stages, and Give Space is "warn, never remove" with the reasoning in the
migration. Analytics send ids and enums only.

Gaps:

- **SMS terms describe handling that does not exist.** The 08-31 commits added
  STOP/HELP language, but there is no inbound Twilio webhook, no opt-out
  column, and reminders go to any `guest_contact` that looks like a phone
  number, including non-users who never opted in.
- **`LEGAL_VERSION` was not bumped.** `src/lib/legal.ts:1` is still
  `'2026-07-29'` while both legal pages say "Effective August 31, 2026", so the
  re-acceptance gate in `proxy.ts:199` never fires for the SMS clause.
- **Signal audience defaults to everyone you know**
  (`20260717130000_multi_audience_signals.sql:65`, `SignalBar.tsx:48`) while the
  README promises "only the circles you choose".
- **Third-party AI hops are not disclosed in flow.** Profile interests go to
  Anthropic in discovery and behavioural reads go in `/you`; the privacy page
  is the only disclosure point.
- **No data export.** Only the host's guest CSV and the calendar feed exist.
- **Five notification categories default on.** Reasonable for a plans app,
  but not the "off by default" posture the product claims elsewhere.

**One loop works at any density and it is the product.** `/create` to the
wizard to the cascade engine to the share link to RSVP to the room to "Run it

**The commits did not follow the docket.** Of the last 40, roughly 11,500 of
17,000 changed lines are new surfaces: a photo-derived theme builder across
four commits and about 3,600 lines (plus three fix commits for it), private
zones, poll trees, the passport, the digest, message search, the heatmap,

and one of those (#156) was adding a back button and a non-scrolling time
picker a month after launch.

**The cold start is not solved.** A user with zero connections sees four
pillars of which three open onto empty rooms, a signal composer that reaches
nobody, and a subtitle asking them to "let people know". The bridge that
exists, inviting non-users by email or SMS through guest links, depends on

## 11. Method

Read-only review of the checkout plus verification against GitHub Actions run
history and job logs, Vercel deployments, runtime error groups, and runtime
request logs. Local `tsc`, `eslint`, `vitest`, and `next build` were run. Five
parallel investigations (security, codebase, UX, vision, operations) produced
findings that were then re-verified at the cited lines before inclusion; every
High security finding and every P0 item was checked by hand. The production
database itself was not reachable from the audit environment, which is why
§2.2 names two candidate causes rather than one.
