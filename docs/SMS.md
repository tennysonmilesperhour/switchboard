# SMS coordination

Members verify their phone and separately subscribe in Settings. SMS invitations carry a random, phone-bound code: `YES <code>` accepts and `NO <code>` declines an outstanding invitation. `CONFIRM <code>` acknowledges an existing accepted RSVP. Codes expire with the notification (24 hours for invitations, one hour for reminders); the invite itself must still be active. A bare YES retains Twilio's opt-in meaning. Required questions and guardian approval direct the member to the app. Capacity checks and room membership share the web RSVP database transition. Duplicate Twilio MessageSids never execute twice or send a second acknowledgment.

Settings offers one channel per plan/reminder category: existing behavior, push, SMS, verified email, or the in-app inbox alone. Existing behavior is preserved until changed. Selecting SMS does not create consent; the subscription must already be enabled. Every queued delivery rechecks the current channel and verified contact. The legacy member invitation email path runs only with existing behavior. Device push permission and category switches still apply. A separately enabled daily digest remains a summary.

Accepted members can opt into SMS during quiet hours for time, place, or address changes when either the old or new start is within two hours. The exception ends at the earlier relevant start. It does not apply to invitations, reminders or announcements. Guest quiet hours are always 22:00–08:00 in the event timezone; member defaults are the same in the profile timezone, with custom hours supported.

For guests, the host shares a personal invitation link. The guest sends its prepared `JOIN <invitation token>` message from their own phone after reading the disclosure. This stores consent for that unclaimed invitation only. It does not create an account, RSVP, or expose the phone to the host. The confirmation includes the invitation link. Event logistics/cancellation and reminder-window triggers enqueue subsequent texts. Consent expires at the earlier of the plan end (start plus six hours when no end is set) or 30 days from subscribing. Claimed invitations stop guest delivery; account SMS preferences remain a separate choice. An existing subscriber's phone cannot be replaced through a forwarded invitation. STOP suppresses all outbound texts, including command responses other than Twilio's own opt-out response. START restores sending only where saved, current consent still applies.

The signed webhook binds account, receiving number, sender, invitation and current verified identity. Parser inputs and acknowledgments contain no arbitrary code execution; replies are XML escaped. Rate limits apply before executing commands or sending acknowledgments. Delivery workers use atomic claims; only explicit SMS throttling rejections retry. Email and ambiguous sends never automatically repeat. RLS and restrictive grants protect routing, consent, jobs and inbound receipt IDs; retention sweeps remove receipt IDs and email jobs after 30 days and expired guest consent after a further 30 days.

Release through the existing migration-first GitHub workflow after CI. The schema health probe checks the new objects. Local tests use PGlite with simulated Supabase platform tables; GitHub runs native Supabase/pgTAP plus authenticated browser journeys. A provider-free test is not evidence that a carrier delivered a real SMS; live command exchanges require an explicitly authorized test recipient.
